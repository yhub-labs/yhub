# Internationalization

**English is the default UI language**; Simplified Chinese is the only translation so far.
Three catalogs: `web/src/i18n/catalogs/*.ts` (web UI), `yhub/locales/*.py` (backend + CLI) and
`tauri/src/i18n.rs` (tray, notifications and the backend-status messages the settings page renders).

**What is translated**: everything the user reads — UI copy, tool names / descriptions / status,
parameter help, MCP tool descriptions, wall-cell titles, CLI help and errors, tray copy.

**What is not**: logs, comments, plugin *content* (a capsule's own page, a remote's file names),
plugin payloads, user data, and the shell's low-level diagnostics — HTTP protocol errors and process
notes ("chunked response truncated", kill/cleanup details) stay in the language of the code, as the
technical detail behind an already-translated message.

## Frontend catalogs

`web/src/i18n/index.tsx` eagerly merges every `catalogs/*.ts` (`import.meta.glob`); each file exports
flat `en` and `zhCN` maps. Catalogs are split by feature: `app`, `common`, `dashboard` (`cards.*`,
`dashboard.*`), `errors` (`api.*`, `bridge.*`), `launcher`, `settings`, `settings-panels`,
and `tools` (`rclone.*`, `rss.*`, `scheduler.*`). Panels for third-party plugins live with the plugins
(`yhub-labs/yhub-plugins/<id>/panel/catalog.ts`) and are not part of this tree.

Third-party plugins ship their own `locales/en.json` + `locales/zh-CN.json` and declare `@key`
strings in `plugin.json`; the host registers them as `plugins.<id>.*` and resolves them before the
manifest is validated (mechanics: [`plugins.md` §9](plugins.md)). They are deliberately not part of
`make verify-i18n` — the plugin repository verifies its own catalogs with `scripts/verify-i18n.py`.
Call `const { t } = useI18n()` in components and `import { t } from './i18n'` outside React
(`api.ts`, helpers); interpolation is `t('launcher.noResults', { query })`.

- Keys are namespaced by feature, `en` is the source and `zhCN` the translation; both maps carry the
  same keys and no key is declared twice across catalogs.
- Translate at render time — no translated module-level constants (`cardRegistry.ts` stores keys).
- `LANGUAGES` / `DEFAULT_LANG` live in `index.tsx`; the choice persists in `localStorage['yhub.lang']`
  and is mirrored onto `<html lang data-lang>`. Settings → General → Language also writes
  `ui_language` (best effort) so the backend and shell follow.

## Backend, CLI and shell

`yhub/locales/*.py` export flat `EN` / `ZH` maps (plus optional `TEXT_EN` for Chinese metadata); use `tr("capsules.not_found", path=relpath)`, and `tr_text()` for `TOOL_META` names and
tile titles still declared in Chinese. Resolution: `YHUB_LANG` → `settings.json:ui_language` → `en`;
`tauri/src/i18n.rs` resolves `ui_language` itself for tray strings.

## Adding keys or a language

1. add the key to the matching `catalogs/*.ts` in **both** `en` and `zhCN` (or add a catalog file)
2. backend/CLI: add it to the matching `yhub/locales/*.py`; shell: add it to `i18n.rs`
3. run `make verify-i18n`: `scripts/verify-i18n.mjs` (all three catalogs: en/zh parity + duplicate
   keys) and `scripts/verify-i18n-display.py` (every Chinese TOOL_META / tile / param string has an
   English entry — a missing one used to be silent)
4. a new locale also needs a `LANGUAGES` entry, branches in `yhub/i18n.py` + `tauri/src/i18n.rs`, the
   parity script extended to it, and an entry in the Settings language selector
